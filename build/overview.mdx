title: "Changing what your agent is"
description: "The harness is a git repository you edit; the next turn runs what you wrote"
---

Your agent is not a settings page. It is a git repository called a **harness**,
checked out on your machine at `~/harness`, and every question the platform has
about your agent — what its prompt says, which model it runs on, which tools it
has, how long it keeps working — is answered by reading that repository at the
moment the question comes up.

So changing your agent is editing a file.

```bash
cd ~/harness
$EDITOR programs/splox/prompts/assistant.md    # what the agent is told
$EDITOR programs/splox/main.py                 # which model, which tools
git commit -am "Answer in Russian by default"
git push origin main                           # publish it
```

The edit is live on this machine as soon as you save it: the next message in the
chat reads the new file. The push is what makes it a **version**, which is what
every new chat on this harness opens on, and what another machine picks up.

## The loop

<Steps>
  <Step title="Edit a file in the checkout">
    `~/harness` is the harness this machine runs, at the commit this run started
    on. Read it, grep it, edit it with ordinary tools. One machine runs one
    harness, so there is nothing else checked out beside it.
  </Step>
  <Step title="Send another message">
    A chat message is a run. When the run starts, the platform asks
    `programs/splox/main.py` who answers, then asks the same file who that agent
    is. Both answers come from the file as it is right now — nothing was frozen
    at publish time, and there is nothing to restart.
  </Step>
  <Step title="Push when it works">
    `git push origin main` publishes the tree as the next version. Runs already
    going keep the version they started on, so a publish never interrupts
    anything. If the tree is not a valid harness, the push is rejected and
    nothing changes.
  </Step>
</Steps>

That is the whole development loop. There is no build, no deploy, no restart,
and no reload button.

## What a harness holds

```
programs/<name>/main.py           declares this program's agents, in python
programs/<name>/hooks/<point>.py  the points of the run loop it takes over
programs/<name>/prompts/*.md      what its agents are told — data the program reads
tools/<file>.py                   tools of your own, one file per group, flat
evals/cases/<name>.yaml           scripted checks, with evals/graders/<name>.py to judge them
requirements.txt                  what your tools need installed
```

Two file names are fixed: `main.py` and `hooks/<point>.py`. Everything else
inside a program directory is the program's own business — the platform never
opens `prompts/`, never opens a second script you put beside `main.py`, and has
no opinion about their format.

A publish needs at least one `programs/<name>/main.py`. A tree with none is
refused: a harness with nothing to run is not a harness. Everything else on that
list is optional.

<Card title="The five pieces" icon="layers">
  A **program** is a directory with a `main.py`. It declares **agents**, one call
  to `agent()` each. Beside it, **hooks** answer the points of the run loop.
  **Tools** are Python functions the agent calls. **Evals** are the checks the
  tree carries for itself. Every one of them is a file in this repository.
</Card>

## What a harness does not hold

The harness is code. Four things that feel like they belong to your agent live
somewhere else:

- **The files your agent writes.** Those are on the machine, in its home
  directory, and they persist there between conversations. `~/harness` is the
  code; `~/` is the work. See [Memory and what persists](/build/memory).
- **Your secrets.** They are injected into the machine's environment. An agent
  reads `$TELEGRAM_BOT_TOKEN`; nothing writes it into a file in git.
- **The platform's tools and skills.** `system:compute`, `system:search` and the
  rest are services the platform runs. Your harness names them; it does not
  contain them.
- **The conversation.** Chats, runs and their messages are the platform's
  records. The harness decides how a turn is shaped, not what was said.

Anything else at the root of the tree that is not a harness file is refused at
publish time, by name, with what it should have been. Markdown at the root is
allowed and never read: the starter's own `README.md`, `PROGRAMS.md`,
`AGENTS.md`, `HOOKS.md`, `TOOLS.md` and `EVALS.md` come with your harness and
travel with it.

## Asked, not stored

This is the one idea the rest of the section rests on. The platform stores an
**address** for a run — the program, and the agent's name inside it — and
nothing else about the agent. The prompt, the model, the provider, the tools,
the iteration cap are all questions it asks `main.py` when it needs them.

The practical consequence is that different edits land at different moments:

| Edit | Reaches a run |
| --- | --- |
| A prompt file, or a field in `main.py` | The next run — the next message in the chat |
| A hook file | The next turn; the server re-imports it when its mtime moves |
| The body of a tool in `tools/` | The very next call to that tool |
| A tool's name, signature or description | The next run; the catalog is asked once per run |
| A hook file you just added | The next run; the list of hooks is asked once, at the start |
| Any of it, for a new chat or another machine | After `git push origin main` |

Inside one run, the agent's declaration is asked once, at the start. That is
deliberate: a loop whose prompt and tools changed under its own turns would be
two runs wearing one name. What *can* change every turn are the hook points —
`context.build` rebuilds the prompt on every turn, `model.choose` names the model
on every turn.

## When it does the wrong thing

The first question is almost always which of your files actually ran, and that is
not something to guess at. A hook that raises does not stop the run: the
platform's own answer runs in its place and the turn continues, which is what you
want in production and exactly what hides a typo while you are writing one.

```
harness_hook_trace
```

It reads the run's journal and answers one line per point: how often the point
was reached, how often your hook did not decide, how many of those were failures
rather than deliberate deferrals, the median duration, and the last few failures
in the hook's own words.
