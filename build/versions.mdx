A harness is a git repository. Not a repository plus a row that says it exists: the
repository **is** the harness, and everything the platform stores about one is a
pointer at it.

So the version history you want is `git log`, and publishing is `git push`.

```bash
cd ~/harness
git log --oneline -5
```

```
9e5d095 Undo the program marker a reaper that no longer exists asked for
4e91ca3 Give the executor the design skill it was being told to read
4902b02 Merge remote-tracking branch 'starter/main'
c151b87 Every agent stopped after sixty passes, whether or not it had finished
e700238 Merge branch 'main' of https://git.splox.io/starters/assistant
```

## The checkout on the machine

Every machine has its harness checked out at `~/harness` — also
`$SPLOX_HARNESS_DIR` — at the commit the current run started on. One machine, one
harness, one directory: a machine that held a directory per harness its owner had
would be a machine carrying every other machine's files.

```bash
cd ~/harness && git remote -v
```

```
origin  https://splox.io/api/v1/harness-git/<user_id>/<harness_id>.git (fetch)
origin  https://splox.io/api/v1/harness-git/<user_id>/<harness_id>.git (push)
```

The address is the pair `owner uuid + harness uuid`, which names any harness
without a lookup. Authentication is already arranged: a credential helper in
`~/.gitconfig` answers with the run's own token, so `git fetch` and `git push` work
with no keys to configure and nothing to paste.

```
[credential "https://splox.io"]
    helper = "!f() { echo username=x; echo password=$SPLOX_API_KEY; }; f"
```

A harness you do not see on this machine is one on a machine of its own. Clone it
by taking any checkout's remote URL and swapping the harness uuid at the end for
the one you want:

```bash
git clone https://splox.io/api/v1/harness-git/<user_id>/<other_harness_id>.git other
```

## The refs

```bash
git ls-remote origin
```

```
9e5d0959bc41d0fcd83e957cf2c0e9c06d75fea9   HEAD
9e5d0959bc41d0fcd83e957cf2c0e9c06d75fea9   refs/drafts/<uuid>
9e5d0959bc41d0fcd83e957cf2c0e9c06d75fea9   refs/heads/main

4e91ca3fe25b881490541c9920a00fe05fde291d   refs/versions/4
```

| Ref | Is |
| --- | --- |
| `refs/heads/main` | The current version — the tree a new chat opens on. |
| `refs/versions/N` | One publish. `N` is decimal from 1, no leading zeros; the next number is one past the highest such ref, read from git. |
| `refs/drafts/<uuid>` | Unpublished work, staged by the git proxy on the way to a publish. |

Your checkout fetches the version refs alongside the branches, so the whole history
is local and addressable:

```bash
git show refs/versions/3 --stat
git diff refs/versions/3 refs/versions/4
```

A version number is a label for people. A tree is named by its **commit**, and the
commit is what a run records.

## Publishing

```bash
cd ~/harness
git add -A
git commit -m "Answer in Russian by default"
git push origin main
```

The push **is** the publish. It goes through the platform's git proxy, which stages
your tree as this chat's draft, validates it, and either makes the next version or
rejects the push with every problem named at once:

- a tree with no `programs/<name>/main.py` to run
- a file the harness has no place for
- two tool files that would be shown under one name
- a case naming a grader the tree does not carry
- a tool file that does not import, quoted in the interpreter's own words

Nothing anybody else runs changes until that push succeeds, and runs already in
flight keep the version they started on. A publish never interrupts anything.

<Warning>
A program's own Python is not read by the gate and not parsed anywhere on the
server: it is code an agent runs in its sandbox, against the checkout. So a
`main.py` that declares an agent the platform cannot serve — a model nobody has
credentials for, a tool slug that does not exist — publishes happily and fails on
the run that needs it. [Checks](/build/evals) is how you find that before a user
does.
</Warning>

### What a publish is not needed for

Nothing on the machine you are already working on. The checkout is what a run
reads, so an edited prompt lands on the next message, an edited hook on the next
turn, and an edited tool body on the very next call — with no publish in between.
The projection also leaves a dirty checkout alone: it will not overwrite work
sitting in the sandbox with the published commit.

Publish when the change should reach a **new chat**, another machine, or anybody
else.

## Reading the versions back

```bash
curl -s -H "Cookie: session=$SESSION" \
  https://<host>/api/v1/harnesses/<harness_id>/versions
```

```json
{
  "versions": [
    {
      "number": 1,
      "commit": "371758ecf28e8240192e4731080a7436fb492a09",
      "message": "created from starters/assistant at c151b87e73304d08c88495cad7d19e4c328e8742",
      "created_at": "2026-09-02T07:04:30Z"
    }
  ]
}
```

That first message is the whole provenance a harness keeps: a harness never comes
into existence empty, and the only gesture that creates one is copying a starter.
The copy is a fresh repository with a fresh history, and the line above is the only
record of where it came from. No column names a starter.

On the v2 API, `GET /v2/harnesses/{harness_id}/versions/{commit}` returns one exact
published tree and its files — every path against that file's contents, the same
bytes the runtime parses to execute the harness. There is no POST counterpart: a
version is created by pushing, which owns the only write path into git.

## Which version a machine runs

A machine names the harness it runs and the ref it takes it from. The app says it
in one line under the machine's name:

<Frame caption="Runs My Agent @ main — this machine takes the harness as it stands, and picks up each publish on its next chat">
  <img src="/images/build/machine-harness-ref.png" alt="A machine card reading 'Runs My Agent @ main'" />
</Frame>

The same pair on the wire:

```bash
curl -s -H "Cookie: session=$SESSION" https://<host>/api/v1/machines
```

```json
{
  "machines": [
    {
      "id": "01a060ee-ffb4-736c-9863-db1fee5c13df",
      "kind": "sandbox",
      "harness_id": "bb088abc-1f04-5282-84d7-1e52c6dbb0cd",
      "harness_ref": "main",
      "name": "My Agent",
      "created_at": "2026-09-02T07:04:30Z",
      "live": {"state": "never_started"}
    }
  ]
}
```

`harness_ref: "main"` is the ordinary case: this machine runs the harness as it
stands, and picks up each publish on its next chat. Pin it to a version ref to hold
it still:

```bash
curl -s -X PATCH -H "Cookie: session=$SESSION" -H 'Content-Type: application/json' \
  -d '{"harness_ref":"versions/1"}' \
  https://<host>/api/v1/machines/<machine_id>
```

An empty `harness_ref` restores `main`. An empty `name` falls back to the harness's.

<Warning>
The ref is not checked against the repository when you set it: a `harness_ref` of
`versions/99` on a harness with five versions is accepted, and the failure shows up
when the machine tries to check that tree out.
</Warning>

A chat carries the same pair, so a conversation from last week is readable at the
tree it actually ran:

```json
"harness": {"id": "...", "name": "My Agent", "commit": "371758e...", "version": 1}
```

`version` is the number of the ref that names that commit, or `null` for a commit
that `main` moved past without a version ref — the chat still runs it.

## Rolling back

A version is immutable and nothing deletes one, so a rollback is a publish that
carries an older tree. Two ways, and they answer different questions.

<Tabs>
  <Tab title="Undo the change">
    ```bash
    cd ~/harness
    git revert 9e5d095          # or: git revert --no-commit <a>..<b>
    git push origin main
    ```
    The next version's tree is the old behavior, and the history says which change
    was undone and when. This is the one to reach for when a change was wrong.
  </Tab>
  <Tab title="Restore a whole tree">
    ```bash
    cd ~/harness
    git read-tree -u --reset refs/versions/3
    git commit -m "Restore version 3: the guard added in 4 refused ordinary shell calls"
    git push origin main
    ```
    `read-tree -u --reset` sets the index and the working tree to that exact tree,
    deleting files added since, and leaves `HEAD` where it is — so the commit that
    follows is a new version whose tree is byte-for-byte version 3's. Use this when
    several changes have to go at once and picking them apart is not worth it.
  </Tab>
  <Tab title="Stop one machine">
    ```bash
    curl -X PATCH -d '{"harness_ref":"versions/3"}' .../machines/<id>
    ```
    Nothing is published and nothing else moves; this one machine reads an older
    tree. Use it to reproduce a bug, or to keep a machine steady while you work on
    `main`.
  </Tab>
</Tabs>

Commits in the checkout are made as `splox <harness@splox.io>` unless you set
`user.name` and `user.email` yourself.

## Keeping up with the starter

Your harness began as a copy of a starter, and its first commit is a child of the
starter's own — so the starter is still upstream, and its improvements can be
brought in whenever you want them:

```bash
git fetch https://<host>/api/v1/harness-git/starters/<name>.git main
git merge FETCH_HEAD
```

Files you never touched arrive silently. A file you did edit conflicts only where
your edit and theirs are in the same place, and you resolve it the way you resolve
any merge.

The starter is read-only to you: a push to it is refused, so nothing you do in your
own harness can change what anybody else's is made of.

## Deleting

Deleting a harness archives its repository. Existing runs and their history stay
readable; new runs against it fail. Nothing in this system issues a repository
delete, and the history survives either way.
